# 互动白板解决方案

## 产品介绍

互动白板是一个实时在线的的共享空间，相较于传统的黑板，不用受空间限制，允许更多的人同时协作和实时互动，团队成员可以同步书写、绘制、突出显示、标记文档，并使用在线白板的其他功能来呈现他们的想法。
![JkfEbxGi1oYYnzxJrPjcyUx8nBf](https://tosv.byted.org/obj/larkparser/lark_cache/202a578d1fdb6d19dee989a31bfc4b56b279f78bfc596d61d1ebf411d8367bee.jpg)

火山互动白板提供一整套完整的互动白板解决方案，客户端 SDK 覆盖 iOS、Android、Web 、小程序等主流平台，同时提供完整的服务端配套功能，可用于在线教育、云端会议、游戏娱乐、金融面签等场景。
**在线教育：**互动白板可广泛应用于线上语言培训、教学辅导、STEAM 教育等线上课堂场景。老师在线上课堂使用互动白板进行的板书、教学演示、绘制等操作将实时同步给学生。同时，学生也可以通过白板反馈学习情况。
**云端会议：**互动白板可应用于在线视频会议、远程培训等企业协同场景。主持人使用白板演示，和其他参会人员进行互动、协同创作。
**游戏娱乐：**互动白板可应用于你画我猜、大家来找茬、互动涂鸦等娱乐场景。
**金融面签：**互动白板可应用于视频面签、远程见证等金融场景，满足面签双方远程办理业务、进行签名确认的需求。

## 业务诉求

在互动白板的4个主要场景中分别有以下的能力诉求：
教育方向的主要能力诉求：
- 板书：对白板书写体验提出了要求，书写顺滑、有笔锋。
- 资料展示：需要将 PDF、PPT 转为可以在白板中展示的格式，并且需要尽量保留动画和还原排版，以及支持多个课件混合使用。
- 辅助工具：数学物理等理工学科需要提供科目工具，比如画三角形、画坐标系和函数等。
- 课堂笔记：支持录制课堂，学生可以回放查看课堂内容。

会议方向的主要能力诉求：
- 资料展示：需要将 PPT 转为可以在白板中展示的格式，并且需要尽量保留动画和还原排版。
- 辅助讨论：提供备注、脑图、流程表、泳道图和小贴纸等功能。
- 内容输出：一般要自己根据白板记录总结成邮件，最多需要支持导出图片作为原始资料。

游戏娱乐的主要能力诉求：
- 笔刷：需要提供多种不同类型的笔刷，比如：铅笔、蜡笔等。
- 录制回放：需要录制笔迹，并生成动图，以分享到社交网络。

金融面签的主要能力诉求：
- 内容保存：提供笔迹保存功能，把笔迹导出为图片。

## 业务分析

在业务场景分析的基础上，我们把业务诉求能力拆分为三个大类：
- 基本能力：板书绘制、实时互动、多人协同。实时同步绘制数据，处理协同产生的冲突，确保每个用户看到一样的内容。
- 扩展能力：在基础能力上，提供回放、动态 PPT、保存涂鸦等扩展能力，满足不同业务场景的诉求。
- 多端支持： Web 端，Android、iOS 移动端，微信小程序，渲染效果保持一致。

在对现有的互动白板市场和开源实现[调研分析](https://bytedance.larkoffice.com/docx/F4WKdkdlpoAnEcxg4YjcxlKgnte)后，我们发现：
- **互动白板具有商业化价值：**教育市场和会议市场对互动白板有较为强烈的诉求。其中教育市场营收场预估国内互动白板市场规模约12亿元，全球互动白板市场规模约为40亿元，会议市场国外头部玩家 miro 估值已超百亿美元。
- **主要竞品均提供自研互动白板产品：**RTC 主要竞品声网、腾讯和即构均提供单独的互动白板产品作为教育场景和会议场景下的RTC增值服务进行搭配售卖。
- **更好的性能与更好的用户体验：**竞品能力主要服务于教育场景下的诉求，均保证低延时的绘制同步体验，而开源白板注重绘制体验，选用延迟较高的 WebSocket 作为消息通信方案，同步体验较差，且无法满足动态PPT、录制回放等教育场景下的功能诉求。

因此，我们决定自研互动白板，复用低延迟的 RTS 网络，打造用户体验最好的互动白板。
## 方案执行

不同场景下虽然诉求的白板能力有差异，但是基本能力的诉求是一致的：提供可以实时互动的板书功能。然后在此基础上扩展功能，满足不同场景的能力诉求。动态 PPT 由于兼容性原因，需要引入外部商业闭源但兼容性较好的 WPS 作为服务提供商，因此放到最后实现。基于此思路，我们的实现路径如下：
1. 搭建整体框架，实现基本功能：绘制、数据同步、协同编辑功能。
1. 模块化实现扩展功能：并行实现录制回放、快照保存多个独立功能，补齐产品能力。
1. 多端统一：采用跨端架构，复用 Web 能力，低成本提供 Android/iOS SDK，满足多端诉求。
1. 动态 PPT：引入外部供应商 WPS 支持动态 PPT 能力，最终提供完整的互动白板解决方案。

### 板书绘制

板书绘制指用户通过鼠标或者手指在屏幕上进行涂鸦绘制， 因此板书绘制需要解决图形绘制和用户输入两个主要问题。

#### 图形绘制

主流的 web 绘制方案有三种：
<table data-lark-table="docx-table" data-block-id="N76tdRYTAoSPCexoJ4Sc8loYnPg"><thead><tr><th>方案</th><th>优点</th><th>缺点</th></tr></thead><tbody><tr><td>SVG</td><td>- 矢量图，缩放不模糊。<br />- 易处理 DOM 事件。</td><td>- 每条笔迹都被视为一个独立的 DOM 元素，大量的笔迹会导致 DOM 膨胀，进而影响页面的性能。<br />- 实时渲染性能低于 Canvas  的像素绘制方式。</td></tr><tr><td>Canvas + 2D</td><td>- 像素级进行图形绘制，适合笔迹绘制<br />- 性能不错</td><td>- 图形元素无法绑定DOM事件，需要额外处理。</td></tr><tr><td>Canvas + WebGL</td><td>- 性能最好</td><td>- 依赖浏览器 GPU 加速，有一定兼容性问题<br />- API 设计复杂，学习曲线较陡。</td></tr></tbody></table>

正如前文所说，白板的业务场景下用户主要使用画笔绘制内容，内容多是不规则图形，且需要再用户绘制过程中实时绘制，SVG 性能无法满足诉求。Canvas + 2D 和  Canvas + WebGL 都满足业务诉求，但是 WebGL 的成本较高，且对设备有一定要求，存在一定的兼容性问题。因此，最终选用 **Canvas + 2D** 方案。

#### 用户输入

**主要问题**：用户输入需要顺滑的笔迹体验，但是通过原生浏览器事件获取到点数量少，直接渲染出来的线条并不丝滑。
**解决方案：** 基于贝塞尔算法在每三个点之间额外补充点，使线条渲染的更丝滑。
[画板](https://bytedance.larkoffice.com/docx/DcnNdeK1KoU0IAxXEh2cqbVZnnc?block_id=BacDdlbqsoqSJlx0JVpcT1TlnTd)

```typescript
// 1. 贝赛尔算法至少需要三个点
// 2. 已上次计算的结束点作为下次计算的开始点
// 3. 使用上个点作为控制点
// 4. 绘制过程中，使用最近两个点的中间点作为结束点，绘制结束后，使用最后一个点作为结束点。
function handle(points, isMove) {
  if (points.length < 2) return [];
  const start = LAST_END_POINT;
  const control = points.at(-2);
  const end = isMove ? half(points.at(-2), points.at(-1)) : points.at(-1);
  const gen = getPathPoint(start, control, end);
  const points = Array.from({ length: 5 }).map((, idx) => gen((idx + 1) / 5));
  LAST_END_POINT = end;
  return points;
}

// 使用贝赛尔算法计算中间点
export function getPathPoint(sp: Point, cp: Point, ep: Point) {
  const { x: x0, y: y0 } = sp;
  const { x: x1, y: y1 } = cp;
  const { x: x2, y: y2 } = ep;

  return function (t: number) {
    return {
      x: Math.pow(1 - t, 2) * x0 + 2 * t * (1 - t) * x1 + Math.pow(t, 2) * x2,
      y: Math.pow(1 - t, 2) * y0 + 2 * t * (1 - t) * y1 + Math.pow(t, 2) * y2,
    };
  };
}
```

### 实时互动

实时互动是指将主讲人的笔迹绘制内容实时同步给观众，延迟需要低于 400ms，否则用户会感受到卡顿。为了实现这一功能，我们需要一个可靠的低延迟网络，因此我们选择 RTS 作为数据传输的通道，并在此基础上优化我们的数据传输策略，以确保良好的用户体验。
#### 数据同步

基于 RTS 能力，通过 ICE 和 DataChannel  建立低延时的全双工网络通道，可以实现实时的数据传输。数据传输时还会通过 Protobuf 序列化来压缩消息体大小，服务端收到数据后验证没有冲突后同步给其他用户，并持久化存储到 DB 中。

#### 收发绘制数据

**核心问题**：绘制期间会产生大量临时数据，在实时传输时对网络和存储都有一定的压力，因此针对绘制中的临时数据需要单独处理。
**解决方案：**
- 把绘制中的临时数据拆分成 **kStart**(开始)、**kOngoing**(绘制中)、**kFinish**(结束) 3个阶段分别处理。
- **降低服务端压力：**kStart、kOngoing 的数据会存储在 Redis 上，只有 kFinsih 了才会把完整的图形数据保存在 DB 里面。

![board_3.png](https://tosv.byted.org/obj/larkparser/image/document_parsing_model/0968c81d-48ae-4357-9ecb-62110f4fcabf.png)

- **降低消息发送压力：**在保证低延时体验的前提下避免发送大量临时绘制数据。** **对 kOngoing 的消息会进行聚合，每 200ms 发送一次。

#### 延迟优化

**主要问题**：互动白板服务最初通过 OpenAPI 接入 RTS 服务，白板服务和 RTS 服务走的都是 HTTP 协议，会额外带来一部分延迟且无法保证消息顺序。
**解决方案：**旧链路中消息达到边缘节点后，先通过  singal access (RTC 内部同步边缘节点消息到中心机房的传输通道)到达中心机房后，在通过 HTTP 协议和白板服务交互。新链路中消息达到边缘节点后，直接通过 singal access 转发到白板服务，不再经过 RTC 中心机房，减少数据传输链路，保证端到端消息延时降低到 100ms 以内。

### 多人协同

多人协同是指多个用户在同一个白板上进行涂鸦，并操作相同的元素。因为多个用户同时操作，所以不可避免地会产生冲突。为了解决不同用户操作产生的冲突，在数据操作时需要添加悲观锁。另一方面，我们需要确保每个用户看到的内容是相同的，这就需要保证内容的一致性和时间的一致性。

#### 处理数据冲突：悲观锁

结合互动白板的业务特点来看：
- 画板是由图形元素组成，各图形元素独立互不影响。
- 通常1-2人操作，其他用户观看。

在调研了业界处理协作冲突的解决方案后，结合以上业务特点，最终采用加悲观锁的方式保证数据不冲突。
锁粒度：
- 白板元素：在白板绘制时锁定当前绘制的白板元素，其他元素不影响。
- 白板：在白板维度上操作时会锁定整个白板，比如：新增、删除、切换白板页。

#### 处理数据丢失：一致性检测

**主要问题**：用户网络情况比较复杂，可能是有线网络、4G或者5G网络，网络状态是不稳定的，随时可能发生丢包，出现数据不一致的问题。
**解决方案：**
- 周期性的检测数据是否一致。
- 为了低成本且快速的检测数据是否一致，我们没有采用全量数据对比的方案，而是通过**对比修改次数**来检测数据是否一致。

[画板](https://bytedance.larkoffice.com/docx/DcnNdeK1KoU0IAxXEh2cqbVZnnc?block_id=C0wwdGAerotPNpxnZ2AciyTTnCg)

#### 时间校准

用户本地时间并不可靠，所以我们使用服务端时间对客户端时间进行校准，保证不同用户的时间一致，进而保证数据一致且有序。
计算接口返回后本地时间和服务端时间的差距（gapTime）：**服务端时间 + (接收到时间 - 发起时间) / 2 - 接收到时间**
后续请求时在本地时间加上 gapTime 以校准时间，从而保证不同用户的操作数据在服务端是有序可靠的。

### 录制回放

录制回放指记录画板上的所有操作并进行有序回放，常用于学生回放课堂内容场景。
**主要问题**：白板操作是一系列增量数据，跳转进度后需要 SDK 从头开始计算得到当前画板的全量数据，大量的计算会导致卡顿，影响用户体验。
**解决方案：**在开始播放回放前生成快照，当用户跳转回放进度时能够快速从快照中恢复当前白板，避免从头开始计算，进而避免卡顿。

- **播放进度丢失：**音视频操作是瞬时操作，不会记录播放状态，导致每次播放都是从头开始播放，播放进度丢失。
- **无法暂停媒体：**暂停回放只是暂停白板操作的回放，不会暂停白板里面媒体元素的播放状态。

**改进方案：**
- **计算媒体状态：**过滤出和音视频媒体元素关联的白板操作，基于这些操作计算出音视频媒体在一个时间点的具体播放状态。
- **插件系统**：引入「插件系统」，把相关逻辑收敛在插件内部，通过 hook 串联流程，和主流程解耦。

### 动态 PPT

在使用互动白板时，主持人需要展示本地 PPT 内容时，需要先对本地 PPT 进行转码，转码成一个在线网页后，通过互动白板展示给观众，观众可以实时观看 PPT 内容并在 PPT 上做些标记和翻页。
动态 PPT 引入 WPS 作为技术供应商，在对接 WPS 过程中，我们发现 WPS 一些设计上的问题：
- **首次加载慢：**WPS  是在第一次打开动态 PPT 文件时去下载原文件并实时转码，对于一些比较大的 PPT，首次加载时间会比较长。
- **缺少预处理**：用户的 PPT 多种多样，不能完全转换成在线网页，比如 PPT 引用了一个本地媒体文件，转换成网页后是无法播放的。而由于 WPS 是在使用时加载，白板无法提前感知 PPT 问题，用户只有使用的时候才能发现问题，重新调整 PPT 原始文件，用户体验不佳。

因此我们搭建了「**动态转码服务**」：
- 通过 Puppeteer 加载 WPS Web SDK，触发 WPS 内部的文件转码机制，以解决首次加载慢问题。
- 通过 WPS Web SDK 提供的能力检查 PPT 原始文件，并自动修复 PPT 中出现的问题，以提升用户体验。

### 多端统一

最开始的 Native SDK 采用原生语言和 C++ 相结合的方式设计开发，这带来了一些问题：
- Native SDK 需要投入 3 个人，开发成本高。
- 多端渲染的一致性难以保障，影响用户体验，客诉多。

**解决方案：**
发起跨端项目，把 Native SDK 迁移到跨端架构，三端底层复用一套代码和能力。
- 在 Native SDK 中嵌入一个 WebView，复用 Web SDK 的能力。
- 在 Web 侧引入了额外的 Hybrid 层，负责和 Native 传输消息，连接 Native  SDK 和  Web SDK。

![board_7.png](https://tosv.byted.org/obj/larkparser/image/document_parsing_model/b7ed2fc3-02fc-45f4-a4b6-c49c0aded220.png)

为减少 API 适配的成本，我们设计了一套通用的消息格式描述类的创建和方法的调用，在后面的迭代过程中，新增的 API 也无需改动 Hybrid 层，只需要在 Native 层适配即可。
API 主要分为创建对象实例和调用对象实例上的方法两种：
1. 客户端先调用创建对象实例的 API，Web 在创建对应的实例对象后，会生成一个唯一的 _instanceId，并将其与实例对象相关联，然后将 _instanceId 返回给客户端。
1. 当客户端调用实例上的方法时，它会将 _instanceId 传递给 Web，Web 使用 _instanceId 找到关联的实例对象，调用真正的实例方法，并将结果返回给客户端。

#### **工程质量**

- 一类是之前测试没有发现的 BUG
- 一类是边界 Case，难以通过人工测试的方式发现

#### 数据指标建设

我们评价一款互动白板产品的好坏，主要关注以下几个方面的核心体验：**实时性、稳定性以及用户体验**。
端到端延迟：
- 定义：一个用户操作后，在另一个用户上展示的延迟。
- 计算：消息发送到白板服务端的网络延迟 + 白板服务端处理的延迟 + 白板服务端广播到远端用户的平均延迟。
- 说明：端到端延迟反映了互动白板的实时性，较低的延迟能提供给用户和线下面授教学相近的互动体验。
- 优化结果：[延迟优化](https://k0n651r40tn.feishu.cn/wiki/QI5xw0hW4iQxWFkRIhWcbHZXnUb#MNaAdNQMTohsxQxLncJc0e28n0f)后延迟从 600ms 降到 100ms。

![UIbZb6j3ooBWQixydPNcDZyrnEc](https://tosv.byted.org/obj/larkparser/lark_cache/86b023eeaacbaf582001bd59580e92012a8fc7440f04e55c90a1afa14c7ca3fa.png)

文件转码成功率：
- 定义：用户发起文件转码任务后，转码任务成功的占比。
- 计算：1 - 转码失败次数(排除因为用户文件原因导致的失败) / 转码发起次数
- 说明：转码成功率反映了互动白板服务的稳定性，较低的转码成功率会阻塞客户流程，降低用户体验。
- 优化结果：静态转码迁移到[新架构](https://bytedance.larkoffice.com/wiki/Rbs6wW7YZi1oj5kow5ZcxvMAnhe)后最终成功率从 96% 提升到 99%，动态转码增加[重试](https://bytedance.larkoffice.com/wiki/Lw5PwJvOeicvvkk0LU4c23SHnNd)后成功率从 82% 提升到 98%。

![AarJb0l08oZhZ0xoEKQcEMfIn4f](https://tosv.byted.org/obj/larkparser/lark_cache/b8b254c5c5da6b534499634342c349e3124afc64cf109b918ae52724270b57e2.png)

加入房间耗时：
- 定义：用户开始加入房间，到用户登录成功，加入到 RTC 房间的耗时。
- 说明：加入房间是用户使用互动白板的必要流程，耗时影响客户使用体验。

此外，我们还构建了以下数据指标：
- 白板/白板页切换耗时：监测常见用户操作的耗时，以反映用户的使用体验。
- 白板数据 packet 成功率：监测数据是否被服务端正确处理，反映用户操作体验。
- SDK API 错误信息：通过监测 SDK API 调用结果和错误反馈，规范 SDK 错误信息，提升客户接入体验。

**主要收益：**
1. 完善埋点数据，建设数据看板20+，比如 packet 的收发正确率、文件转码成功率等看板。
1. 优化了关键指标，端到端延迟从 600ms 降到 100ms，静态转码成功率从96%提升到 99%，动态转码成功率从 82% 提升到 98%。
1. 为产品提供了明确的指标数据，和竞品数据持平，增强了产品销售和推广的信心。

这种场景下，互动白板作为内容的提供方，需要满足几个需求：
1. 主讲人的绘制数据可以被抓取。
2. 主讲人可以进行资料展示，包括 PPT、PDF 等。
3. 主讲人页面上其他 UI 元素不应该出现在直播流中，比如：个人信息，操作面板等。

其中，需求二要求能够抓取动态 PPT 的内容。目前，Web 端主流的动态 PPT 展示解决方案是基于 **DOM +**** iFrame** 实现的。如果要抓取 DOM 内部的变化，由于浏览器的限制，只支持两种方式：
1. 利用浏览器提供的 [MediaDevices.getDisplayMedia](https://developer.mozilla.org/zh-CN/docs/Web/API/MediaDevices/getDisplayMedia) API 获取整个屏幕的流，然后把整个的屏幕抓取推送给用户，但是会导致抓取到很多无关内容。
1. 一个是利用 html2Canvas 之类的库，把 DOM 先转化为 Canvas，然后使用[captureStream](https://developer.mozilla.org/zh-CN/docs/Web/API/HTMLCanvasElement/captureStream) 进行采集，最大的问题是 html2Canvas 非常的消耗性能，页面会十分的卡顿，以及整体的效率达不到“观看不卡顿”的要求。

以上两种方式都无法满足业务需求，因此我们采用了云端录制的方案：在本地采集摄像头流，并通过云端无头浏览器采集互动白板和动态 PPT 流，然后将这两路流合并为一路流推送给观众。具体方案如下图所示：

拆解流程如下：
1. 业务端决定是否开启云端录制，在云端让另外一个“隐身人”加入和主讲人相同的房间，云端渲染一个只包含白板的页面。
1. 无头浏览器开始抓自己的屏幕流，然后和 Web 端本地采集的摄像头流一起推入到一个 RTC 房间当中。
1. 在这个房间内把两路流合并为一路流。
1. 把合并完的流推向 CDN，进而推送给观众。

这样就完成了一个直播场景下，主讲人使用白板和资料展示能力，并对观众进行讲解的完整流程。
这套方案通过云端录制的方式，在云端浏览器渲染一个只包含白板的页面，并通过无头浏览器抓取屏幕流，避免抓取到无用元素内容。
业务收益
1. PPT中的动画操作在用户体验上是不可替代的。因此，在会议和多人协作场景下，完整的资料展示能力是一个非常重要的需求。通过满足此需求，可以有效满足用户的诉求。
1. 在直播场景中，针对资料展示中的细节进行讲解和圈画是一个非常强烈的需求，而白板有效地满足了这一需求。
1. 增加了云端录制的计费，为业务带来额外营收，同时该方案也成为未来商业化拓客的样板 Case。

# 未来规划

## 产品规划

互动白板产品的主要能力已经和竞品持平，但是和竞品仍然有一些差距，存在一些问题
1. 缺少大规模使用验证，还有部分问题没有暴露。
1. 产品能力和客户诉求仍存在一些 Gap，需要补齐。
1. Demo 相对竞品简单，教育会议场景化 Demo 缺少关键的 PPT 能力，客户接入成本较高。

因此为了达成“**业界最好用的互动白板**”目标，我们认为可以长期投入的方向：
1. 到客户实际业务场景中去，去深入理解互动白板在实际业务场景和使用，发现客户诉求和产品能力的 Gap，尽早补齐。同时介入到产品设计中，提供技术专业的视角。
1. 整理互动白板相关技术实现，对外分享输出，建设技术品牌，以便触及更多的潜在客户，最终实现产品从 1 到 N 的突破。
1. 完善场景化 Demo，快速开始 Demo，UIKit 的建设，降低客户的接入成本，提升 OnBoarding 体验。

## 技术规划

由于历史原因，互动白板的技术设计仍有较多不合理的地方：
1. 大类问题，核心的 WhiteBoard、WhiteBoardRoom 类超过 1k 行，承载了太多功能。
1. 模块藕合，渲染和数据分层不清晰。
1. 缓冲机制队列机制不完善，在弱网环境下可能会有边界异常 Case 出现。

技术改造是为了提升 SDK 质量，必然会涉及到对现有逻辑的改造，为了避免出现 Break Change，
1. 首先我们要去梳理现有的逻辑，明确其中的细节，通过文档和单元测试的方式落地。
1. 在有了单测的基础后，我们在去重构解决大类，数据和渲染不一致的问题。
1. 之后以模块的方式来拆分和组装 SDK，各个模块之间高内聚性和低耦合性，以提高 SDK 的灵活性和易用性。
