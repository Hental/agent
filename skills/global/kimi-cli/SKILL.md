# Kimi Code CLI

把 Kimi Code CLI 当作“编码执行器”，由当前 Agent 负责规划、约束、监控和验收：

```text
当前 Agent：理解需求、检查仓库约束、拆解任务、制定验收标准
    ↓
Kimi Code CLI：在指定工作目录中分析、生成或修改代码并运行验证
    ↓
当前 Agent：检查 git diff、验证结果、处理遗漏并向用户总结
```

不要只转述 Kimi 的回答。当前 Agent 始终对权限边界、工作区安全和最终质量负责。

## 1. 执行前检查

先确认 Kimi 可用：

```bash
command -v kimi
kimi --version
```

如果命令不存在，停止并说明需要安装 Kimi Code CLI。不要在未获用户同意时自动安装软件。

如果出现未登录或凭证失效，执行：

```bash
kimi login
```

登录通常需要用户在浏览器或设备授权页面完成确认。等待用户完成，不要读取、打印或转存凭证。

进入目标仓库后，先完成以下检查：

1. 阅读仓库内的 `AGENTS.md`、`CLAUDE.md`、`README.md` 或等效约束文件。
2. 运行 `git branch --show-current` 和 `git status --short`。
3. 识别用户已有的未提交修改，并在给 Kimi 的提示中要求保留它们。
4. 确认任务是否只允许分析，还是允许修改文件。
5. 把终端工具的 `workdir` 设为目标项目目录；不要依赖 `cd` 后的隐式状态。

工作目录必须在启动 Kimi 前已经存在。优先使用目标仓库根目录或更窄的任务目录；不要把 Kimi 启动在主目录、多仓库的上层目录或其他范围过大的目录中。

## 2. 选择执行模式

### 默认调用参数

- 默认模型为 `k3-256k`，本机 CLI 对应的完整模型别名为 `kimi-code/k3-256k`。每次新建或恢复执行会话都显式传入 `--model kimi-code/k3-256k`，不依赖 `config.toml` 或历史会话中的模型默认值。
- 默认使用 YOLO 模式，显式传入 `--yolo`；标准启动命令为 `kimi --model kimi-code/k3-256k --yolo`。无需修改本机默认配置。
- 本机 CLI 的 YOLO 是 Ask When Needed：常规编辑和命令自动执行，风险操作、问题和计划仍可能询问；不要擅自替换成 `--auto`。
- 默认优先选择支持上述参数的交互模式，即使任务可以一次完成。仅在任务确实需要非交互输出时使用 One-shot；仅分析或用户要求先出计划时使用 Plan。这两个模式按下文省略不兼容的 `--yolo`，仍显式指定模型。
- 用户明确指定其他模型或执行模式时，以本次用户要求为准。

模型参数接收已注册的完整别名；裸写 `--model k3-256k` 会在发送第一条任务时失败，即使启动界面显示了该名称。显式选择模型不依赖默认模型配置，但仍需要本机存在对应的模型和 provider 配置。

### One-shot 模式

适合目标明确、无需中途回答问题、可以一次完成的修改或调研：

```bash
kimi --model kimi-code/k3-256k -p "任务描述"
```

当前 Kimi Code 的 `-p`/`--prompt` 是非交互模式，会在完成后退出。此模式默认按自动权限策略处理常规工具调用，所以只能在可信且范围明确的工作目录中使用。

使用终端工具执行时：

- 将 `workdir` 明确设为目标项目目录。
- 给小任务设置约 5 分钟的等待预算，复杂任务设置 10 分钟或更长。
- 初次调用的等待时间保持在 30 秒以内；如果命令仍在运行，使用返回的会话 ID继续轮询。
- 非交互模式通常不需要 PTY；如果当前平台的输出异常或命令挂起，再改用 PTY。

不要给 `-p` 同时添加 `--plan`、`--yolo` 或 `--auto`，这些参数组合会被 Kimi 拒绝。

需要机器解析输出时使用：

```bash
kimi --model kimi-code/k3-256k -p "任务描述" --output-format stream-json
```

只有后续确实要解析事件流时才使用 `stream-json`；面向人检查时优先使用默认文本输出。

### Plan 模式

适合只允许分析、需要先给方案、风险较高或需求仍可能变化的任务：

```bash
kimi --model kimi-code/k3-256k --plan
```

Plan 模式是交互 TUI，必须使用 PTY。启动后把任务发送到会话，并在 Kimi 给出计划后停止在审批点。未经用户授权，不要批准退出 Plan 模式或开始写文件。

Plan 模式会限制常规文件写入工具，但 shell 命令仍按权限规则处理；提示中仍要明确禁止产生修改的命令，并监控审批请求，不能把 Plan 模式当作绝对沙箱。

如果用户只要求诊断原因，不要把诊断自动扩展成修复。优先使用当前 Agent 的只读检查；确实需要 Kimi 深度分析时，使用 Plan 模式。

### 交互模式

适合复杂任务、多轮澄清、长时间运行或 Kimi 可能主动提问的场景：

```bash
kimi --model kimi-code/k3-256k --yolo
```

使用支持持续会话的终端工具时：

1. 以 `tty: true` 在目标 `workdir` 启动 `kimi --model kimi-code/k3-256k --yolo`。
2. 保存返回的会话 ID。
3. 使用终端输入工具发送任务和后续回答。
4. 每次等待不超过 30–60 秒，并定期检查新输出。
5. Kimi 提问时，只回答任务范围内且已有依据的问题；会改变实现方向、扩大权限或产生高风险写入的问题交给用户决定。
6. 任务完成后正常退出；仅在卡死或明确需要中止时发送中断信号。

恢复当前目录最近的会话：

```bash
kimi --model kimi-code/k3-256k --yolo --continue
```

选择或恢复指定会话：

```bash
kimi --model kimi-code/k3-256k --yolo --session
kimi --model kimi-code/k3-256k --yolo --session SESSION_ID
```

只有确认旧会话与当前任务、当前工作目录一致时才恢复，避免继承无关上下文。

## 3. 构造高质量任务提示

给 Kimi 的提示应包含：

```text
目标：
  用一句话说明要交付什么。

工作目录与范围：
  指定允许检查和修改的目录、关键入口文件。

仓库约束：
  要求先读取 AGENTS.md 等项目说明；保留现有未提交修改。

功能要求：
  分点列出行为、输入输出、兼容性和边界情况。

禁止事项：
  说明不能修改的文件、不能执行的外部写操作、不能扩大到的范围。

验收标准：
  列出必须运行的格式检查、类型检查、测试或 smoke check。

完成输出：
  要求总结修改文件、关键设计、验证结果和仍存在的风险。
```

示例：

```text
先读取仓库中的 AGENTS.md 和相关模块。修复订单详情页重复请求问题。

范围：
- 只修改订单详情页及其直接依赖
- 保留工作区现有未提交修改
- 不创建或切换分支，不提交代码

要求：
1. 先定位重复请求的触发链路和根因
2. 实施最小修复，避免改变正常刷新逻辑
3. 增加或更新针对该场景的测试
4. 运行相关类型检查和测试

完成后列出修改文件、根因、验证命令与结果；不要声称运行了未实际执行的检查。
```

提示中明确命令版本，例如项目只提供 `python3` 时写 `python3`，不要模糊写成 `python`。

不要把未经处理的用户文本拼接进 shell 命令。需要动态构造较长提示时，使用终端工具提供的参数或安全引用方式，避免命令替换、变量展开和引号注入。

## 4. 监控与交互

Kimi 超过终端工具单次等待时间仍在运行是正常情况，不要因此重复启动相同任务。保存并继续使用原会话：

1. 读取新增输出。
2. 判断是在正常执行、等待审批、等待回答、失败重试还是已经完成。
3. 对正常执行的任务继续轮询。
4. 对明确问题发送简洁、单义的回答。
5. 对权限升级、删除数据、覆盖用户修改、发布、提交或外部写操作，遵循当前用户请求与仓库规则；缺少授权时停止。

不要让用户在超过 60 秒的执行期间得不到进展信息。简要报告当前阶段、已完成事项和下一步。

如果 Kimi 的输出出现终端控制字符或 TUI 局部刷新，关注稳定的文本内容和最终状态，不要把原始噪声完整转发给用户。

## 5. 错误处理

### 429 或配额限制

如果输出包含 `429`、`rate_limit_error` 或明确的配额耗尽信息：

1. 停止短时间重复调用。
2. 把任务标记为受配额限制，而不是代码执行失败。
3. 告知用户已完成到哪一步，以及恢复后需要补跑什么。
4. 只有用户要求立即继续时，才由当前 Agent 在授权范围内接手剩余工作，并明确区分哪些结果不是 Kimi 产出。

不要猜测固定恢复时间；以错误信息显示的重试时间或账户配额页面为准。

### 登录或配置错误

先运行：

```bash
kimi doctor
```

只报告必要的诊断信息，不展示 token、Cookie、API Key 或配置文件中的敏感字段。

### 命令长时间无输出

依次检查：

1. 会话是否仍在运行。
2. 是否缺少 PTY。
3. 是否在等待审批或用户输入。
4. `workdir` 是否存在且正确。
5. 是否错误地重复启动了多个相同会话。

确认卡死后再中止，不要直接遗留后台进程。

### Kimi 修改超出范围

立即停止继续执行，先检查 `git diff` 和未跟踪文件。不要使用 destructive git 命令回滚，也不要覆盖用户原有修改。说明越界文件和可能影响，由用户决定如何处理。

## 6. 验收与交付

Kimi 完成后，当前 Agent 必须独立核验：

1. 运行 `git status --short`，确认实际修改范围。
2. 阅读 `git diff`，检查是否包含无关改动、占位实现、调试日志或敏感信息。
3. 按仓库说明运行最相关的格式检查、类型检查、测试或 smoke check。
4. 对 Kimi 声称成功但没有证据的步骤重新验证。
5. 确认没有遗留的 Kimi 交互会话或后台进程。

向用户交付时说明：

- Kimi 完成了什么。
- 当前 Agent 复核了什么。
- 实际运行的验证命令和结果。
- 未能验证的事项、剩余风险或阻塞。

不要把 Kimi 的成功退出等同于任务完成；以仓库状态和验证结果为准。

## 7. 常用命令速查

```bash
kimi --model kimi-code/k3-256k --yolo   # 默认：显式指定模型和 YOLO
kimi --model kimi-code/k3-256k --plan                  # 从只读规划开始
kimi --model kimi-code/k3-256k -p "任务"               # 单次非交互任务
kimi --model kimi-code/k3-256k --yolo --continue              # 继续当前目录最近会话
kimi --model kimi-code/k3-256k --yolo --session               # 交互选择历史会话
kimi --model kimi-code/k3-256k --yolo --session SESSION_ID    # 恢复指定会话
kimi doctor                  # 检查配置
kimi login                   # 登录
kimi upgrade                 # 升级
```
