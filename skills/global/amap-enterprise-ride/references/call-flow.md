# 企业打车呼叫流程

完成行程配置后使用本流程。未经本流程要求的确认，不得提交订单。

## 呼叫前确认

在最终的 `呼叫N种车型` 按钮前停止，使用 `lark-card` 技能向 `liutao.fe@bytedance.com` 的已核验 Botmux 私聊发送交互确认卡片。具体发送入口、按钮回调及结果读取按该技能的 [按钮确认](../../lark-card/references/button-confirmation.md) 执行。默认使用飞书按钮完成本次确认，无需再让用户在 Codex 对话中重复批准。

### 卡片内容

先运行 `snapshot <前缀>`，以最新截图和结构化状态生成卡片，标题为 `企业用车 · 呼叫前确认`，正文包含：

- 准确的起点和终点。
- 完整预约日期、上车时间及 `Asia/Shanghai` 时区。
- 车型、已选供应商/服务档位及数量 `N`。
- 当前预估价格区间，明确标出用于后续阈值判断的预估上限 `M`。
- 支付状态 `本单为企付`、个人支付 `0 元`。
- 本次确认编号、快照时间和确认有效期；有效期不得超过预约上车时间。
- 提示：`确认后将按以上信息呼叫这 N 种车型；拒绝则不提交本次呼叫。`

卡片必须有两个可处理回调的按钮：`确认呼叫` 和 `拒绝`。截图应显示订单汇总和最终按钮，优先随卡片发送；发送入口不支持内嵌图片时，用 `lark-card` 在同一私聊发送截图并附相同确认编号，卡片正文仍须保留上述全部行程信息。不要发送只有按钮、没有行程信息的提问。

### 发送与处理结果

1. 按 `lark-card` 核验收件人和完整会话 ID。先确认发送入口能接收并读取按钮结果，再发送；仅有展示卡片能力时不能宣称已建立确认流程。
2. 将本次确认编号、快照路径、完整行程和价格、预期点击者身份、有效期及发送/回调结果保存到项目根目录 `.reports/amap-enterprise-ride/<本次确认编号>/`。自定义卡片另保存发送成功返回的 `messageId` 和 `sessionId`；内置提问保存本次命令与结果的对应关系。
3. 等待该卡片的结果。确认必须来自已核验收件人，并对应当前确认编号、当前消息/提问及尚未过期的快照。发送成功、已读、按钮存在、历史确认或等待超时都不是批准。
4. 用户点击 `确认呼叫`：记录有效确认，立即重新读取页面，确认仍为 `pre_call`、不存在活动订单、预约时间未过期，且路线、时间、车型、供应商/服务档位及数量、价格和支付状态与卡片完全一致。符合时继续下方提交步骤，不再重复询问同一次确认。
5. 用户点击 `拒绝`：结束本次呼叫流程，回执 `已拒绝，本次未呼叫车辆`。拒绝仅表示不提交本次呼叫，不代表授权取消已有订单，也不要自动重新发卡。
6. 发送失败、回调不可用、结果无法核验、确认过期或参数发生变化时，不得提交。参数变化使旧确认失效；重新配置和取快照后生成新编号、新卡片并等待新确认，不得复用旧卡片的批准。
7. 对同一卡片的重复回调只处理一次。自定义卡片在确认、拒绝或失效后，由插件返回状态卡片或用 `botmux card patch` 原地标记结果并移除操作按钮；状态为 `已确认，待核验并呼叫` 时不能提前写成预约成功。内置提问由 Botmux 管理按钮状态，并通过 `lark-card` 发送处理结果回执。标注 `testOnly: true` 的测试卡片结果不得用于真实呼叫。

卡片回调只记录用户决定，不直接操作 ADB 或提交订单；呼叫仍由持有本次最新页面状态的执行流程完成。

确认后遵守当前界面工具的财务操作策略。如果允许代理完成，则只点击一次最终按钮；如果策略要求用户接管，则请用户完成这一次点击，然后恢复监控。在首个订单状态不明确时，绝不能再次提交。点击后立即读取状态；出现加载中、弹窗或未知状态都不代表失败，不得再次点击最终按钮。

## 下单弹窗处理

点击最终呼叫按钮前，记录当前已选车型的预估价格上限 `M` 和用户确认的价格上限。若下单时出现“实际支付金额超出 `T` 元的部分，需要您个人支付”一类弹窗：

1. 从弹窗中读取个人支付阈值 `T`，不要使用历史阈值或猜测数值。
2. 重新读取当前已选车型的预估价格上限 `M`，并确认路线、预约时间、供应商数量和 `本单为企付` 均未变化。
3. 运行 `confirm-threshold <用户确认上限>`。脚本仅在 `M < T`、`M` 不超过用户确认上限且页面仍显示 `本单为企付` 时点击弹窗“确认”。
4. 脚本返回 `stop`、退出码 4、无法解析字段或页面发生变化时，不要手工绕过；停止并向用户确认。

例如：当前已选预估上限为 101 元，弹窗阈值为 106.14 元，因为 `101 < 106.14`，可以自动确认继续。

## 呼叫后监控

1. 确认页面已从呼叫前状态切换到正在派单、搜索司机或活动订单。
2. 运行 `monitor --interval 15 --timeout 900 --prefix <截图前缀>`，或大约每 15 秒读取一次订单状态。仍在搜索时，至少每分钟向用户更新一次。
3. 司机接单、派单失败、用户取消或应用要求作出重要选择时停止轮询。
4. 司机接单后立即发送：
   - 供应商/平台
   - 页面显示的司机姓名
   - 车辆颜色、品牌和型号
   - 完整车牌号
   - 司机预计到达时间/距离
   - 已确认的上车点和预约时间
   - 当前截图
5. 无法读取的字段明确标记为“暂不可用”，不得猜测车牌或司机身份。

修改行程、接受付费升舱、实际增加个人支付或取消活动订单前，必须询问用户。仅当下单弹窗满足上述 `M < T` 规则时，可以自动确认阈值提示。

## 司机接单后飞书通知

司机接单信息向用户确认后，使用 `lark-card` 向 `liutao.fe@bytedance.com` 的已核验 Botmux 私聊发送结果卡片，卡片发送与更新统一由 Botmux 中转。

1. 卡片包含平台/供应商、司机姓名、车辆颜色/品牌/型号、完整车牌、上车点、终点、预约日期和时间、支付方式（本单为企付），并关联最新截图。
2. 通过 `botmux send --session-id <已核验的完整会话ID> --no-mention --card-file <结果卡片绝对路径>` 发送；截图按 `lark-card` 发送到同一私聊。
3. 仅当司机已接单（状态为 `assigned`）且用户已在对话中收到接单信息后才发送，不得提前宣称成功。核验返回的 `success` 和 `messageId`，发送失败不阻塞订单本身，仅如实提示飞书通知未送达。

## 恢复与幂等

- 设备离线时先恢复连接，再读取当前页面；不要把 ADB 失败当作下单失败。
- 应用重启后先检查活动订单。看到预约成功、司机、车牌或取消行程入口时，直接进入监控，禁止重新配置和提交。
- 仅当最新结构化状态明确为 `pre_call` 且不存在活动订单时，才允许执行最终呼叫。
- 使用 `tap-text <文本> --timeout <秒>` 等待异步页面；不要复用旧 XML 坐标。
