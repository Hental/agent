# Mac mini M4 32GB 本地大模型部署

> 本文记录这台 Mac mini 的本地模型选型、资源瓶颈，以及 `qwen3.8:27b` 的 Ollama 部署信息。设备和模型信息以 2026-08-31 本机实测为准。

## 1. 当前设备

| 项目 | 配置 |
| --- | --- |
| 设备 | Mac mini（Mac16,10） |
| 芯片 | Apple M4 |
| CPU | 10 核：4 个性能核 + 6 个能效核 |
| 统一内存 | 32GB |
| 架构 | arm64 |
| 本地运行器 | Ollama 0.33.0 |

Apple Silicon 使用统一内存，CPU、GPU 和系统共享这 32GB。运行大模型时，模型权重、KV Cache、视觉投影模型、Ollama 本身和其他应用都从这 32GB 中分配空间。

## 2. 能部署多大的模型

这台机器的舒适区是 7B–14B 的量化模型；20B–27B 可以运行，但需要控制上下文长度并关闭占用大量内存的应用；32B 及以上通常不适合作为日常 Agent 模型。

| 模型规模 | 建议量化 | 适用情况 |
| --- | --- | --- |
| 7B–9B | Q4、Q5 或更高精度 | 运行轻松，速度快，适合常驻 Agent 和一般工具调用 |
| 12B–14B | Q4 或 Q5 | 质量、速度和内存占用比较均衡 |
| 20B–24B | Q4 | 可以使用，长上下文会明显增加内存压力 |
| 27B | Q4 | 可运行但接近本机实用上限，最好专机运行 |
| 32B 以上 | 极低量化或部分卸载 | 不推荐，速度、上下文和系统可用内存都受明显限制 |

这里的“可以运行”不代表能按模型宣称的最大上下文运行。例如模型支持 262K 上下文，也不代表 32GB 内存能够实际承载 262K KV Cache。

## 3. 当前瓶颈

首要瓶颈是 **统一内存容量和带宽**，不是 CPU 核数。

- 27B Q4 权重本身约占 16GB，视觉投影模型还需要约 888MB。
- 上下文越长，KV Cache 占用越大；多会话并发还会进一步放大内存使用。
- macOS、Ollama 和其他应用也需要统一内存。UTM 虚拟机、Android 模拟器、浏览器和开发工具会与模型争抢内存。
- 内存不足后会触发内存压缩和 Swap，生成速度可能骤降，并增加系统卡顿。
- CPU 主要影响提示词处理、模型调度和未完全交给 GPU 的运算；模型持续生成时通常更受内存带宽影响。

运行 27B 模型前，建议关闭 UTM 和 Android 模拟器，并把初始上下文设为 8K–16K；确认内存余量后再逐步提高。

## 4. Q4、Q5 量化是什么意思

量化是用较低位数保存模型权重，以减少磁盘、内存和计算开销。

- **Q4**：权重大体按 4 bit 表示。文件更小、内存占用更低、速度通常更快，质量会有少量损失。
- **Q5**：权重大体按 5 bit 表示。质量通常略好于 Q4，但模型更大、内存占用更高。
- **Q8**：更接近高精度模型，但所需内存显著增加。
- **FP16/BF16**：高精度权重，27B 模型仅权重通常就超过 50GB，不适合这台 32GB Mac mini。

`Q4_K_M` 中：

- `Q4` 表示以 4 bit 为主的量化。
- `K` 表示 llama.cpp 的 K-quant 分组量化方案，会根据张量重要性采用不同处理。
- `M` 表示 Medium 变体，在文件大小和质量之间取中间方案。

因此，`Q4_K_M` 通常是消费级设备部署大模型时较稳妥的默认选择。对这台机器而言，7B–14B 可以考虑 Q5；27B 更适合 Q4_K_M。

## 5. 27B 以下的 Agent 模型选择

Agent 模型除了对话能力，还应重点检查：工具调用、结构化输出、指令遵循、代码能力、上下文效率和推理速度。

| 优先级 | 模型方向 | 适合用途 | 本机建议 |
| --- | --- | --- | --- |
| 1 | Qwen 7B–14B 工具调用模型 | 中文 Agent、代码、工具调用、结构化输出 | Q5 或 Q4，适合常驻 |
| 2 | Qwen 20B–27B 工具调用模型 | 更复杂的规划、代码与多模态任务 | Q4，单会话使用 |
| 3 | DeepSeek 蒸馏版 7B–14B | 推理、数学、代码 | 先验证工具调用格式的稳定性 |
| 4 | GLM、Kimi、MiniMax 的开放权重小型版本 | 中文长文本或特定工作流 | 仅选择 27B 以下且有 Ollama/llama.cpp 兼容量化的版本 |

选择 GLM、Kimi、MiniMax 或 DeepSeek 时，不能只看厂商品牌。很多最新旗舰模型是云端 API 模型、超大 MoE 模型，或没有可用的 Ollama/llama.cpp 权重，不能直接在这台机器本地部署。应只保留同时满足以下条件的型号：

1. 开放并可下载模型权重；
2. 总参数或实际激活内存适合 32GB 统一内存；
3. 存在 Ollama 支持或兼容的 GGUF/MLX 量化版本；
4. 支持所需的工具调用、结构化输出或视觉能力；
5. Q4 模型加 KV Cache 后仍能给 macOS 留出足够内存。

当前本机已经验证可部署的是 `qwen3.8:27b`。如以 Agent 的响应速度和稳定性优先，7B–14B 通常比 27B 更适合作为默认模型；27B 更适合复杂任务的按需升级路由。

## 6. Ollama 是什么

Ollama 是本地大模型运行器和模型管理工具，主要负责：

- 下载、保存、加载和删除模型；
- 在 Apple Silicon 上调用本机计算资源进行推理；
- 管理模型量化、模板、参数和上下文；
- 提供命令行交互和本地 HTTP API；
- 为 Agent、网页应用和开发工具提供统一的模型接口。

默认 API 地址是 `http://localhost:11434`。本地运行时，输入内容默认不需要发送给模型厂商；但调用联网工具或第三方应用仍应单独检查其隐私策略。

常用命令：

```bash
# 查看已安装模型
ollama list

# 运行模型
ollama run qwen3.8:27b

# 查看模型元数据
ollama show qwen3.8:27b

# 查看当前已加载的模型
ollama ps

# 停止模型
ollama stop qwen3.8:27b

# 删除模型及其不再被引用的数据
ollama rm qwen3.8:27b
```

## 8. 模型文件位置

Ollama 使用内容寻址存储，模型权重按 SHA-256 摘要命名，因此不会出现一个名为 `qwen3.8-27b.gguf` 的文件。

模型清单：

```text
/Users/liutao/.ollama/models/manifests/registry.ollama.ai/library/qwen3.8/27b
```

主模型权重，约 16GB：

```text
/Users/liutao/.ollama/models/blobs/sha256-f5f1dd8920d417aac2718b0bda3403da274301efdd6760b4f0f4b864ff2ad57d
```

视觉投影文件，约 888MB：

```text
/Users/liutao/.ollama/models/blobs/sha256-ac3714bfdddeca31351f2752bf1a63f266f4df87c0b68c895e44945ca704448e
```

完整模型目录：

```text
/Users/liutao/.ollama/models
```

可以用 Finder 打开：

```bash
open /Users/liutao/.ollama/models
```

不要手动移动、重命名或删除 `blobs` 中的文件。模型清单通过摘要引用这些 Blob，手动修改可能破坏模型；应使用 `ollama rm` 管理模型。

## 9. 运行与基础测试

运行前先关闭 UTM、Android 模拟器以及其他占用大量内存的应用，然后执行：

```bash
ollama run qwen3.8:27b
```

测试本地 HTTP API：

```bash
curl http://localhost:11434/api/chat \
  -d '{
    "model": "qwen3.8:27b",
    "messages": [
      {"role": "user", "content": "你好，请简要介绍自己"}
    ],
    "stream": false
  }'
```

运行期间观察模型加载和 CPU/GPU 分配：

```bash
ollama ps
```

观察系统内存压力：

```bash
memory_pressure
```

如果出现明显 Swap、系统卡顿或生成速度突然下降，应依次降低上下文长度、减少并发、关闭其他应用，最后再考虑更小的模型。
