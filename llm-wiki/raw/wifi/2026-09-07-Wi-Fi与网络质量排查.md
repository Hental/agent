# Wi-Fi 与网络质量排查

整理日期：2026-09-07。来源：本次关于“网络不好、卡顿究竟是 Wi-Fi 还是外网问题”的讨论，以及仓库内网络诊断工具的实现。

## 核心结论

“网络不好”不是单一故障。一次完整访问至少经过：终端 → Wi-Fi 无线链路 → 路由器/局域网 → 光猫与宽带 → DNS/代理/VPN → 互联网目标服务。排查的关键不是先重启或改配置，而是从近到远逐层测量，找到从哪一层开始出现丢包、延迟或吞吐异常。

最有效的区分方法是同时比较到网关和到公网的持续 Ping：

| 现象 | 优先判断 |
| --- | --- |
| 到网关已经丢包、延迟高或波动大 | Wi-Fi、终端、AP/Mesh 或路由器局域网问题 |
| 到网关稳定，到公网开始异常 | 路由器 WAN、光猫、宽带或运营商问题 |
| IP 访问正常，域名访问异常 | DNS、代理或 VPN 问题 |
| 基础测试正常，只有特定应用卡顿 | 应用服务、CDN、代理规则、浏览器或终端负载问题 |
| 空闲时正常，一上传/下载就卡 | 带宽被占满或缓冲膨胀 |
| 只有一个设备异常 | 该终端的网卡、驱动、系统配置或后台任务问题 |
| 所有设备同时异常 | AP/路由器、光猫、宽带或上游网络问题 |

## 如何判断 Wi-Fi 质量

Wi-Fi 质量不能只看“信号格数”或测速峰值，应同时观察以下指标：

| 指标 | 参考范围 | 说明 |
| --- | --- | --- |
| RSSI 信号强度 | ≥ -60 dBm 较好；-60 至 -70 dBm 可用；< -70 dBm 较差 | 数值越接近 0 越强 |
| SNR 信噪比 | ≥ 40 dB 较好；25–40 dB 可用；< 25 dB 易不稳定 | 比单看信号更能反映干扰 |
| 到网关丢包 | 理想为 0%；持续 > 1% 明显异常 | 最直接的本地无线链路证据 |
| 到网关平均延迟 | 通常应低于 10 ms | 还要关注最高延迟和抖动；偶发尖峰会造成卡顿 |
| 协商速率 / MCS | 用于观察连接档位变化 | 不等于真实吞吐，只能作为辅助证据 |
| 信道和频宽 | 观察同信道、邻信道竞争 | 2.4 GHz 覆盖远但更拥挤；5/6 GHz 通常更快但穿墙较弱 |
| 实际吞吐 | 用有线端 `iperf3` 测局域网 | 公网测速会混入宽带和运营商因素 |

单次测速正常不能排除间歇性卡顿。最好在问题发生时连续采样 30–100 次 Ping，并分别在靠近 AP、原故障位置、不同终端、网线直连等条件下做对照。

## 其他常见原因

- 无线环境：距离远、墙体遮挡、同信道竞争、2.4 GHz 蓝牙/微波炉干扰、频宽过大、自动信道选择不佳。
- AP/Mesh：无线回程弱、漫游粘连到远端节点、节点摆放不合理、负载过高、固件问题。
- 终端：省电策略、网卡或驱动异常、同时启用多个接口、重复 IPv4、后台同步/下载、CPU 或内存占用。
- 路由器与光猫：NAT/连接数压力、散热或电源异常、QoS 配置不当、端口协商异常、双重 NAT。
- 宽带与运营商：线路质量、上行拥塞、晚高峰拥塞、跨网路由、运营商 DNS 或目标方向故障。
- 软件链路：代理、VPN、Fake-IP、DNS 污染或超时、防火墙、浏览器扩展、安全软件。
- 目标服务：应用服务器、CDN 节点、区域性故障、限速或服务端处理变慢。
- 业务特性：视频更依赖稳定吞吐，游戏和会议更怕延迟、抖动与丢包，网页则同时受 DNS 和连接建立速度影响。

## 推荐排查顺序

1. 记录故障时间、位置、设备、应用，以及是否所有设备都受影响。
2. 持续 Ping 默认网关，确认终端到路由器的本地链路是否稳定。
3. 同时 Ping 公网 IP，比较异常是否只出现在网关之后。
4. 分别测试域名解析和公网 IP，隔离 DNS、代理和 VPN。
5. 在靠近 AP、切换频段/节点、换终端后复测，确认是否与无线位置或设备相关。
6. 通过网线直连路由器或光猫复测，用有线结果隔离 Wi-Fi。
7. 检查上传/下载负载和 `networkQuality` responsiveness，排查带宽占满与缓冲膨胀。
8. 仅在证据指向某一层后，再调整信道、节点、DNS、代理、路由器或联系运营商。

如果路由器管理地址是 `192.168.10.101`，管理页面可补充查看当前信道、频宽、终端连接节点、Mesh 回程、WAN 状态、端口协商和系统日志。但终端侧的分层测试仍应保留，因为管理页面的“在线”状态不能证明链路没有丢包或延迟尖峰。

## 仓库内诊断工具

脚本位置：`apps/network-diagnose/network-diagnose.mjs`。当前仅支持 macOS，执行只读采集，不登录路由器，也不修改网络配置。默认采集 Wi-Fi 状态、附近无线网络、路由、接口、网关与公网 Ping、DNS、系统代理和 Apple `networkQuality`。

在项目根目录执行：

```bash
pnpm install
pnpm zx apps/network-diagnose/network-diagnose.mjs
```

默认报告写入 `.reports/network-diagnostics/`，同一次采集会产生：

- `network-report-<时间>.md`：适合人工查看的采集报告。
- `network-report-<时间>.json`：包含解析结果和各命令原始输出的结构化数据。
- `network-report-<时间>.codex.md`：Codex CLI 可用时生成的分层分析。

常用参数：

```bash
# 增加采样次数
pnpm zx apps/network-diagnose/network-diagnose.mjs --ping-count 100

# 明确指定网关或 Wi-Fi 接口
pnpm zx apps/network-diagnose/network-diagnose.mjs --gateway 192.168.10.101 --interface en0

# 只采集，不调用 Codex 分析，也不运行带宽测试
pnpm zx apps/network-diagnose/network-diagnose.mjs --no-analyze --skip-network-quality

# 自定义输出路径；JSON 和 Codex 分析沿用同一文件名主体
pnpm zx apps/network-diagnose/network-diagnose.mjs --output .reports/network-diagnostics/manual-check.md
```

`networkQuality` 会产生实际网络流量并在短时间内占用较多带宽，不适合在重要会议或其他延迟敏感任务进行时运行。

## Web UI 查看报告

查看器位于 `apps/network-diagnose/viewer/`，使用 Vue 3 和 Arco Design，通过 unpkg 加载依赖。应从项目根目录启动静态服务器，避免浏览器对本地文件的读取限制：

```bash
python3 -m http.server 8080
```

然后访问 `http://127.0.0.1:8080/apps/network-diagnose/viewer/`。页面可以导入 Markdown 报告和对应的 `*.codex.md`，展示 Wi-Fi 信号、SNR、网关/公网延迟、信道竞争、诊断项和原始证据。原始 JSON 目前主要供程序化分析和后续扩展使用。

## 结论边界

一次采样只代表当时状态，无法证明间歇性问题已经消失。协商速率不能替代局域网吞吐测试，公网测速也不能单独区分 Wi-Fi 与宽带问题。定位时应保留时间、地点、设备和网络负载等上下文，并以重复、对照实验为准。
