发送前用 `botmux list --plain` 查找当前会话，按 AppID 与 chat_id 精确匹配；不要永久依赖本文中的会话 ID。示例中的占位符需替换为已核实的完整会话 ID：

```bash

botmux send --session-id <session-id> --no-mention --content-file /absolute/path/message.md
```

发送成功需检查退出状态以及 `success`、`messageId`、`sessionId`。自定义卡片的按钮回调需要相应插件实现，不能仅凭卡片已发送就认为按钮功能可用。更新记录或技能本身不代表授权额外发送测试消息。

管理 token 存放于 `/Users/liutao/.botmux/.dashboard-token`，服务端签名密钥位于 `/Users/liutao/.botmux/.dashboard-secret`。不要将其内容写入知识库、技能或通知。

Dashboard 使用 URL 查询参数 `t` 完成 token 登录，并设置 `botmux_dashboard_token` Cookie（HttpOnly、SameSite=Lax）。token 必须放在 `#` 路由片段之前，形式为：

```text
https://<dashboard-host>/?t=<token>#/bot-defaults
```

此前提供的链接将 `?t=...` 放在 `#/bot-defaults` 后面；URL 片段不会随 HTTP 请求发送给服务器，无法按该服务端登录路径建立鉴权 Cookie。分享链接时应避免泄露管理 token。

Dashboard 默认的 `publicReadOnly` 只读访问策略与管理鉴权是两件事；本次未修改该策略。飞书 `allowedUsers` 不会自动把 Dashboard 限制为同一飞书账号。

## Kimi 切换与启动故障修复

用户要求将 Mini 从 Codex 改成 Kimi Code。使用本机已安装的 `/Users/liutao/.kimi-code/bin/kimi`，未重新安装 Kimi；`kimi doctor` 检查通过，独立单次调用成功返回 `KIMI_READY`。随后保存 `cliId: kimi` 和对应路径。

首次托管启动反复报错：

```text
Kimi 在 1 分钟内崩溃 4 次，已停止自动重启。
zsh:shift:1: shift count must be <= $#
```

隔离 tmux 复现实验发现：直接启动登录交互 zsh 时参数数量为 2，tmux 内同类 zsh 启动参数数量变为 0；跳过 zsh 启动配置或使用 `/bin/sh` 后参数数量恢复为 2。证据指向 tmux 环境下的 zsh 交互初始化影响参数，未进一步证明是哪一条 shell 集成脚本导致。

修复仅将 Mini 的 `launchShell` 改为 `/bin/sh`，没有修改用户的 `.zshrc`。重启 Botmux 并恢复 Kimi 会话后，观察到同一 Kimi 进程持续运行 79 秒，tmux pane 未退出；之后输入策略重启后的会话状态为 `idle`，驻留会话数为 1。上述是启动与短时运行验证，不代表长期稳定性测试。
